# Issue #9: Enrollment: check the service before using up the server's steps

- **Date:** 2026-11-12
- **Branch:** agent/9-service-check-first
- **Action log:** `.claude/logs/2026-11-12.log` on the owner's computer (every step, with times)

## What was asked
The app asks the service for a nonce only at the end of enrollment, after the server's step token is used. If the service fails then, every retry fails with `invalid_step` or `invalid_credentials`. Check the service when the link is pasted, before calling the server, and on `invalid_step` go back to the setup screen with the link filled in.

## Plan (planner)
- `enrollLink` calls `Service.Status()` before contacting the server. `Status()` uses the same pipe as `Nonce()` and stores nothing in the service. If it fails, the error shows on the setup screen and nothing is sent to the server.
- If the server answers `invalid_step` to `enroll/start`, `enroll/mfa` or `enroll/finish`, the app goes back to setup with the link filled in (`View.Link`) and keeps `Replacing`.
- The `invalid_step` text becomes "Press Continue to start again", in Arabic and English.
- Test support: `fakeserver` gets `Requests()` and `ExpireSteps()`, and the harness can switch the service off.
- Only the app changes: not the protocol, the service or `internal/ipc`.

Not covered, noted for the owner: `invalid_credentials` after a used-up step. In sign-in, `signInOTP` clears `c.signin` on error, so after `invalid_step` the code screen stays but further codes are ignored; that is a separate issue.

## What changed (implementer)
- `internal/app/app.go`:
  - `enrollLink` trims the link, then calls `Service.Status()` before contacting the server.
  - New `enrollment.raw` field holds the pasted link.
  - New `enrollFail()`: on `invalid_step` from `EnrollStart`, `EnrollMFA` or `EnrollFinish`, it goes back to setup with `Link` and the same `Replacing`. Other errors keep the current screen.
- `internal/app/view.go`: new `View.Link` field, never logged.
- `internal/ui/web/assets/app.js`: when entering setup with `view.link`, the field is filled and focus goes to Continue.
- `internal/ui/web/assets/i18n.js`: `invalid_step` now says "Press Continue to start again" (Arabic and English).
- `internal/fakeserver/fakeserver.go`: new `Requests()` and `ExpireSteps()`, for tests only.
- Tests added or changed:
  - `TestEnrollServiceDownAtLink`, `TestEnrollStepExpiredReturnsToSetup` and `TestEnrollStepExpiredWhileReplacing`; all three failed before the change.
  - The harness can switch the service off (`h.svc.down`).

## Review (reviewer)
- Rounds: 1
- Blocking findings and how they were fixed: none. The reviewer ran `make check` again and it passed, and ran the enrollment tests 3 times with `-race`. Checked against the real server (`../Hifaz`):
  - `enroll/start` and `enroll/mfa` don't use up the link; `enroll/finish` removes it only on success (`internal/service/client_calls.go:265-270`), so prefilling the link and "Press Continue" are correct.
  - `Status()` fails exactly like `Nonce()` and stores nothing.
  - The busy state is cleared and `Replacing` is kept.
  - The link is never logged.
- Notes left for later:
  1. **After two-step setup was saved:** once `enroll/mfa` succeeds, a retry on the MFA screen gets `invalid_step` at once, not after a timeout (Hifaz `enroll.go:229`). The text "This step timed out" is then inaccurate. After Continue, the password screen marks the code as optional, but it is now required; leaving it empty gives `invalid_credentials`, which counts toward lockout. This is the likely cause of the five `invalid_credentials` in the original log.
  2. **The fakeserver accepts a second `enroll/mfa`; the real server refuses it.** That hides note 1 from the tests, and is why `TestEnrollStepExpiredReturnsToSetup` needs `ExpireSteps()`.
  3. **Untested paths:** `enrollFail` is only tested through `enroll/mfa`. Missing tests: `invalid_step` from `enroll/finish`, and `invalid_code` on the MFA screen staying there.
  4. If `enroll/finish` succeeded on the server but the answer was lost, the retry ends with `invalid_link`. That case existed before, and the message is honest.
