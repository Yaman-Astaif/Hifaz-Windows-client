# Issue #21: Split tunnel: names outside the Hifaz DNS zone don't resolve; send all DNS to Hifaz while connected

- **Date:** 2026-11-14
- **Branch:** agent/21-dns-all-names
- **Action log:** `.claude/logs/2026-11-14.log` on the owner's computer (every step, with times)

## What was asked
With a split tunnel the app sends only names under the server's search domains to Hifaz DNS, so private names outside the zone (`hifaz dns add app.example.com. IP`) don't resolve, while the WireGuard app with the same user works. The owner decided: while connected, send all DNS to the server's DNS servers, as the WireGuard app does; routes stay split, no server or protocol change.

## Plan (planner)
- `NewPlan`: when DNS servers exist, set the interface DNS to them and one NRPT rule for `"."`, for split and full tunnels alike. Search domains are kept; with no servers nothing changes.
- New `Plan.DNSOutsideTunnel`: servers not inside `allowed_ips`, worked out without Windows calls. `configureDNS` logs them and still applies; the Group Policy log text is updated.
- Tests: `plan_test.go` (split with and without search domains, full, none, server outside the tunnel), `tunnel_windows_test.go` (the rule's namespace is now `"."`).
- Docs: `docs/architecture.md` DNS bullet, README (`internal/tunnel` line, Decisions), `docs/testing.md`, `Plan` comments.
- Only the service changes: no protocol, server, installer or `third_party` change.

Noted by the planner: while connected, Hifaz DNS sees every lookup, as with the WireGuard app; DNS-over-HTTPS set by hand in a browser still bypasses this. A split tunnel with an IPv6 DNS server on a machine with IPv6 disabled now fails to come up, the same as a full tunnel and WireGuard.

## What changed (implementer)

With no servers, nothing is set. New field `DNSOutsideTunnel`: servers no `allowed_ips` prefix contains. Field comments say why.
- `internal/tunnel/tunnel_windows.go`: `configureDNS` logs the servers outside the tunnel's routes and still applies; the Group Policy message now says names may not resolve through Hifaz DNS.

## Review (reviewer)
- Round 1 blocking findings:
  1. With the `"."` rule, a dead tunnel (sleep past idle or time limit, peer removed) leaves the machine without DNS; the app can't resolve its server, retries forever and never takes the tunnel down. Fix: the HTTP client remembers the server's last resolved addresses and dials them when a lookup fails (TLS still on the host name); manual check added to `docs/testing.md`.
  2. The security model and README didn't say that every server now sees and can answer every lookup while connected, even without full-tunnel permission, or that other VPNs' adapter DNS is affected while connected. Fix: docs.
- Also fixed from the notes: interface DNS cleared before the adapter closes; clearer log text for a DNS server outside the tunnel's routes.
- Round 2: no blocking findings; the reviewer ran `make check` again and it passed. Verified from the Go source: on Windows a failed or timed-out lookup is a `*net.DNSError`, and the fallback dial gets its own 15 s, well inside the app's 80 s poll timeout. TLS name, SNI and pinning are unchanged.
- Rounds: 2
- Notes left for later:
  1. **The remembered address can be overwritten by Hifaz DNS while connected.** If Hifaz DNS gives a private answer for the server's own name (`hifaz dns add vpn.example.com. 10.98.0.1`) and the connection is re-dialed while connected, the private address is remembered; after a dead tunnel the fallback then fails too and the retry loop returns. Signing out or quitting still recovers. Suggested fix: don't remember addresses inside the tunnel's `allowed_ips`, or only learn before the tunnel is up. The new threat-table row in `docs/architecture.md` doesn't mention this case yet.
  2. `Reconfigure` resolves a changed endpoint host through Hifaz DNS while connected; with a private answer for the endpoint name, the tunnel would break. Rare (the endpoint must change mid-session).
  3. Interface DNS cleared on Down, the rule's contents and removal: only Windows CI (`TestTunnelUpDown`) and the manual checks confirm these.

## Protocol (protocol-keeper)
IN STEP. The wire format, endpoints, signatures, versions and vectors are unchanged, and the vector files are identical. `scripts/interop-hifaz.sh ../Hifaz` passed. The remembered-address dialer still checks TLS against the host name (§2). Sending all names to `dns.servers` fits §9, and Hifaz DNS forwards every name outside its zone upstream. Optional, not required: a sentence in §9 of `../Hifaz/docs/client-protocol.md` saying apps send all names to `dns.servers` while connected.

## Left open
- Review note 1 (remembered address overwritten by a private answer for the server's own name) should be a follow-up issue before 0.2.x release, with the docs caveat.
- Review note 2 (endpoint re-resolved through Hifaz DNS) noted only.
- **Idle timeout:** the server detects idle by silence on the tunnel. Background lookups by Windows and apps now go through the tunnel, so the idle timeout will rarely fire on a normal desktop (the same as the WireGuard app with `DNS =`). The manual idle-timeout check may fail for this reason.
- Manual checks on Windows (`docs/testing.md`): the `"."` rule, a private name outside the zone resolves, sign-out restores normal DNS, another VPN keeps working, and sleep past idle then resume.
- `.claude/agents/reviewer.md` still says "DNS (NRPT) only for the ranges the server sent"; for the owner.
