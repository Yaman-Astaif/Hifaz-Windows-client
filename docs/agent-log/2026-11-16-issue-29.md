# Issue #29: "Connected" with no traffic and no DNS when another VPN's kill switch blocks Hifaz: wait for the server's answer and say why

- **Date:** 2026-11-16
- **Branch:** agent/29-server-answer
- **Action log:** `.claude/logs/2026-11-16.log` on the owner's computer (every step, with times)

## What was asked
When another VPN (the WireGuard app's kill switch on a full tunnel) blocks Hifaz, the app shows "Connected" while no traffic flows, and the NRPT `.` rule leaves the whole computer without DNS. Apply DNS only after the first handshake, show "the server doesn't answer" instead of Connected, and, using a read-only WFP check, name WireGuard's kill switch as the reason when it is there. The owner confirmed the cause on 2026-11-15: unticking "Block untunneled traffic" makes Hifaz work.

## Plan (planner)
- **Service:** interface DNS and the NRPT `.` rule are applied only after the first WireGuard handshake. A small state machine in `internal/daemon/link.go` (no Windows code; states: waiting / up / no_answer) runs every second from a new `Engine.Run`. It removes DNS while the server doesn't answer and puts it back when it does. The limits are named constants: first answer within 10 s; the handshake counts as lost after 3 min with traffic being sent plus 15 s grace; a probe at most every 10 s; the blocker re-checked every 60 s.
- **Handshake trigger:** one probe packet (a DNS query) to an address inside the tunnel, sent only at sign-in and while there is no answer. There is still **no PersistentKeepalive**, as protocol section 8 requires, so the idle timeout and time limit work as today.
- **Why no answer:** a read-only WFP check (`FindKillSwitch`) that runs only while there is no answer. It finds the WireGuard app's kill switch by its rules, not by their names: a provider named `WireGuard` with a block-all filter in the outbound connection layers (ALE connect, IPv4 and IPv6). It names the tunnel through the permit filter for its adapter. The decision logic is in `internal/tunnel/killswitch.go` (tested everywhere); the WFP calls are in `wfp_windows.go`. Any error means the general text.
- **Local IPC only:** `ipc.Status.Link` and `Blocker`. The client protocol is unchanged.
- **App:** `SessionView.Link` and `Blocker`; refresh every second while not up; tray tips for waiting and no answer; English and Arabic texts in the connected card.
- **Docs:** `docs/architecture.md` and `docs/testing.md`. `CHANGELOG.md` is left to the owner.

Decided by the planner:
- **Not built:** detecting a kill switch turned on *while already connected*. WFP blocks before the adapter, so the counters can't show it; catching it needs a periodic WFP check while up. Suggested as a follow-up issue.
- **Built:** the probe can cause one handshake at sign-in or after a failure, which the server counts as activity. The protocol check confirms this fits section 8.
- The tray uses the not-connected icon while there is no answer. The Arabic text keeps the WireGuard option name in English: «Block untunneled traffic».

## Protocol (protocol-keeper)
**IN STEP** at the last commit. Nothing under `internal/protocol/` changed, the vectors are identical, `MinServerVersion` is unchanged, and `Link`/`Blocker` stay local to the pipe and the window.
- The first check was **OUT OF STEP** on behaviour: the endless probe could keep a server session from going idle (section 8). The 90 s probe window fixed this; the re-arm when a kill switch goes away was checked again and is in step.
- **Optional, the owner decides:** a clarification in `../Hifaz/docs/client-protocol.md` section 8, Idle:
  > Received handshake packets count as activity. An app may send a packet into the tunnel to start a handshake (at sign-in, after a server key change, or after a change the app can observe: the server stopping answering, a local blocker going away), but only for a limited time, never while a handshake is current.

  No Hifaz issue was filed, because the client does not need it.

## Left open
- **BLOCKING (review round 3, not fixed):** `internal/tunnel/wfp_windows.go:107`. `wfpCall(p, args ...uintptr)` is an ordinary function, so `uintptr(unsafe.Pointer(&x))` arguments do not keep `engine`, `h`, `n` and `tmpl` from moving. Escape analysis (`GOOS=windows go build -gcflags=-m ./internal/tunnel/`, checked by the coordinator) shows only `entries` and `k` moved to the heap. If the goroutine's stack grows, WFP writes handles and counts into freed stack memory in the LocalSystem service. The fix is one line: `//go:uintptrescapes` above `func wfpCall`, or direct `p.Call(...)` calls at each call site. After the fix, `-gcflags=-m` should show `engine`, `h`, `n` and `tmpl` moved to heap.
- **Windows confirmation needed:**
  - WFP enumeration as LocalSystem sees the WireGuard app's filters;
  - the probe starts a WireGuardNT handshake;
  - WireGuard's adapter alias is the tunnel name;
  - the CI tests listed under Checks.
- **Not built, by plan:** a kill switch turned on while Hifaz is already connected. WFP blocks before the adapter, so the counters can't show it; DNS stays and fails until sign-out. A follow-up issue needs a periodic read-only check while up.
- **Not checked:** a WireGuard tunnel without a `/0` route breaking Hifaz.
- `node` is not installed here, so `app.js` and `i18n.js` were checked by reading only.
