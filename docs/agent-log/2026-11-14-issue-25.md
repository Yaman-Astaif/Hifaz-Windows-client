# Issue #25: Endpoint check: match the full-tunnel rule, accept public addresses and literal endpoints

- **Date:** 2026-11-14
- **Branch:** agent/25-endpoint-check
- **Action log:** `.claude/logs/2026-11-14.log` on the owner's computer (every step, with times)

## What was asked
When the endpoint host changes mid-session, `Reconfigure` refuses an answer inside the tunnel's routes. The issue asks for the same full-tunnel rule as `policy.FullTunnel`, refusing only non-public answers (private, CGNAT, unique-local, link-local), skipping the check for literal endpoint addresses, and saying in the log and `docs/architecture.md` what is assumed.

## Plan (planner)
- Service only: `EndpointInside` becomes `RefuseEndpoint(host, ep, allowed)` in `internal/tunnel/plan.go`, called from `Reconfigure`.
- It refuses only DNS answers (not literal endpoint addresses) that are private, CGNAT (`100.64.0.0/10`), unique-local or link-local, and that fall inside the routes. IPv4-mapped addresses are unmapped first.
- Full-tunnel exemption: reuses `policy.FullTunnel`, per address family (so `/0`, the `/1` pair and four `/2` all count).
- The log reason and the `docs/architecture.md` row now say the private answer is an assumption.
- The planner raised one question: with a full tunnel plus a narrower private range, should a private answer still be refused? The issue already answers it ("when the routes cover the whole space for the endpoint's family, the check doesn't apply"), so the answer is followed. Two existing test rows flip to false.

## What changed (implementer)
Commit `7361e9a`, service only.
- `internal/tunnel/plan.go`: `EndpointInside` is replaced by `RefuseEndpoint(host, ep, allowed)`, plus `nonPublic` and the `cgnat` prefix. A literal host is never refused. IPv4-mapped answers are unmapped first. Only private, CGNAT, unique-local or link-local answers inside the routes are refused. A family that the routes cover completely (`policy.FullTunnel`, however split) is never refused. The old `Bits() > 1` rule is gone.
- `internal/tunnel/tunnel_windows.go`: `Reconfigure` calls `RefuseEndpoint`. The comment and log line now say the private answer is *assumed* to come from the server's DNS and to be reachable only through the tunnel. `Up` is unchanged.
- `docs/architecture.md`: the "Endpoint resolving inside the tunnel" row is rewritten the same way and lists what is followed: public addresses, literal endpoints and full tunnels.
- Tests added or changed: `TestEndpointInside` is replaced by the table `TestRefuseEndpoint` in `internal/tunnel/plan_test.go`, with 10 refused and 15 accepted cases:
  - private, CGNAT, unique-local and link-local addresses, IPv4 and IPv6;
  - public addresses inside routed public ranges, and the CGNAT boundary;
  - IPv4-mapped addresses and wrong-family routes;
  - full IPv4 tunnels as /0, the /1 pair, four /2 and 256 /8, and three /2 with a gap;
  - full IPv6 tunnels as ::/0, the /1 pair and four /2;
  - literal hosts.

## Review (reviewer)
- Rounds: 1
- Blocking findings and how they were fixed: none.
- The reviewer checked that `cfg.EndpointHost` is always a canonical literal (no brackets, port or zone; `parseEndpoint` in `internal/protocol/config.go`) or a normalised name, so the literal skip is reliable. `policy.FullTunnel` is applied per family, as in `NewPlan`.
- Notes left for later:
  - **Deliberate change:** with a full tunnel plus a narrower private range (for example `0.0.0.0/0` and `10.98.0.0/16`), a private answer for the endpoint name is now followed. Before, it was kept. The issue asked for this ("the check doesn't apply" under full coverage). If Hifaz DNS answers with the server's inside address, the tunnel stops until the next configuration or sign-in.
  - Existed before this change: a looked-up answer that is loopback, unspecified or multicast (for example a DNS sinkhole answer of `0.0.0.0`) is followed. Literals are already rejected by `usableUnicast`. It would be cheap to also refuse these in `RefuseEndpoint`; that is a possible follow-up issue.
  - Number-like names such as `1.2.3` are treated as names, so they get the check rather than the literal skip. This is harmless.
  - Doc wording: "the next sign-in resolves again". More precisely, the next configuration carrying that host is looked up again.
