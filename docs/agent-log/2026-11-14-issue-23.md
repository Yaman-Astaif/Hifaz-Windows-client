# Issue #23: Dead tunnel: remembered server address can be replaced by Hifaz DNS's private answer while connected

- **Date:** 2026-11-14
- **Branch:** agent/23-remembered-address
- **Action log:** `.claude/logs/2026-11-14.log` on the owner's computer (every step, with times)

## What was asked
Since #21 every lookup goes to Hifaz DNS while connected, and the HTTP client remembers the address it last connected to so it can reach the server when a lookup fails. A reconnect while connected can replace that address with Hifaz DNS's private answer for the server's own name; after a dead tunnel the fallback then fails too and the app retries forever. Never remember an address that goes through the tunnel; also decide on `Reconfigure` resolving a changed endpoint through Hifaz DNS.

## Plan (planner)
- `rememberingDialer` keeps the **first** address reached for each `host:port`, for the life of one HTTP client. Each sign-in builds a new client whose first dial is before the tunnel is up, so no answer from Hifaz DNS is remembered. Checked: sign-in, the code step, follow, renewal, logout, enrollment, app restart. The `allowed_ips` option was rejected as extra plumbing for no real gain.
- Tests: a dialer test that a later in-tunnel address doesn't replace the first; an app test that each sign-in gets a new HTTP client before the tunnel is up.
- Note 2, in the service: `Reconfigure` keeps the current endpoint and logs when a changed endpoint host resolves inside `allowed_ips` (it would loop and break the tunnel); a port-only change reuses the current address. Tested helper in `plan.go`.
- Docs: the dead-tunnel row in `docs/architecture.md` plus the endpoint rule; a manual check with a private answer for the server's own name in `docs/testing.md`.
- No protocol, IPC, installer, `.github`, `third_party` or `.claude` change.

## What changed (implementer)
- `internal/protocol/dial.go`: `DialContext` stores an address only when none is remembered yet for that `host:port`; the type comment says why (each sign-in builds a new client whose first dial is before the tunnel is up) and that clients must not be reused across sign-ins.
- `internal/protocol/client.go`: `NewHTTPClient` comment says "first reached".
- `internal/tunnel/plan.go`: new `EndpointInside(ep, allowed)`. It ignores the full-tunnel cover ranges (`Bits() <= 1`), because the driver never sends the tunnel's packets into its own interface, so a public endpoint inside a full tunnel is normal. Only narrower ranges count.
- `internal/tunnel/tunnel_windows.go`, `Reconfigure`:
  - same host, new port: keeps the current address, no lookup;
  - new host that resolves inside the narrower routes: keeps the current endpoint and host, and logs "new endpoint resolves inside the tunnel; keeping the current one" with the address and reason; the next config version tries again;
  - a failed lookup fails as before.
- `docs/architecture.md`: dead-tunnel row (first address in this sign-in, never one learned through Hifaz DNS, the remaining LAN edge) and a new row "Endpoint resolving inside the tunnel".
- `docs/testing.md`: the sleep-past-idle variant with a private answer for the server's own name, and an optional endpoint-change check.
- Tests added or changed:
  - `dial_test.go`: `TestDialerKeepsFirstAddress` (replaces the "refresh" test) and `TestDialerEachPortKeepsItsOwnFirstAddress`; both failed before the change.
  - `app_test.go`: `TestEachSignInUsesNewHTTPClient` (sign in with the code step, sign out, sign in again; each tunnel Up sees a client built for that sign-in). It guards the rule above; it passed before too.
  - `plan_test.go`: `TestEndpointInside`, 15 cases (v4, v6, v4-mapped, no routes, full-tunnel cover alone and with narrower ranges).
- During the build I decided one point the plan missed: with a full tunnel every address was "inside", so a normal public endpoint change would have been refused. The full-tunnel cover ranges are now ignored.

## Checks
- `make check`: pass
- Other tests run: `TestEachSignInUsesNewHTTPClient` with `-race -count=3`. The `Reconfigure` endpoint path runs only on Windows and has no automated test; it is in the manual checks.

## Review (reviewer)
- Rounds: 1
- Blocking findings: none. The reviewer ran `make check` again and it passed. Traced and confirmed: password sign-in, the code step, follow, renew, logout, enrollment, adding a server, restart and a second sign-in all make the client's first dial before the user's own tunnel is up (another Windows user is refused with `ErrBusy`). The DNS cache is flushed on tunnel down. `Reconfigure` runs under the tunnel lock, keeps both endpoint and host when it refuses, and a failed lookup changes nothing.
- Notes left for later:
  1. `EndpointInside` ignores only ranges of /1 or shorter, while `policy.FullTunnel` treats any set covering the whole space as full (for example four /2). A legitimate public range routed through the tunnel that contains the server's address (e.g. `198.51.100.0/24`) also counts as "inside". In those cases a mid-session endpoint change is refused and the log reason is wrong. Rare (the endpoint must change mid-session) and the next sign-in recovers, since `Up` has no such check.
  2. The new architecture row states "only reachable through the tunnel" as a fact; it is an assumption (normally a private answer from Hifaz DNS).
  3. A literal endpoint address inside a narrower range is refused by `Reconfigure` but accepted by `Up` at the next sign-in. Harmless but inconsistent.
  4. The `Reconfigure` endpoint branches are Windows-only with no automated test; Windows CI and the manual checks confirm them.
  5. A private answer cached by Windows (Hifaz DNS TTL 60 s) can delay the fallback by up to about a minute after resume; it heals itself.

## Protocol (protocol-keeper)
Not needed. `internal/protocol/dial.go` only changes which remembered address the transport keeps; the client API, wire format, `docs/client-protocol.md`, the test vectors and versions are unchanged. #22's protocol check (IN STEP, interop passed) covered the dialer itself.

## Left open
- Review notes 1–3: one small follow-up could use the same full-tunnel rule as `policy.FullTunnel`, refuse only answers that aren't public, skip the check for literal addresses, and soften the architecture row. Not done here, to keep this change reviewed as planned.
- Manual checks on Windows (`docs/testing.md`): sleep past idle with a private answer for the server's own name after a reconnect while connected; optionally an endpoint change to a name with a private answer. During the first, a cached private answer can delay recovery by up to about a minute.
