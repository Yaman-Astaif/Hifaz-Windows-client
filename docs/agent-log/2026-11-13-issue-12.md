# Issue #12: Sign-in code screen ignores new codes after an error

- **Date:** 2026-11-13
- **Branch:** agent/12-signin-code-step
- **Action log:** `.claude/logs/2026-11-13.log` on the owner's computer (every step, with times)

## What was asked
After the server asks for a code at sign-in, any error clears the code step but keeps the code screen, so Connect then does nothing. Decide per error: keep the step for a wrong code and for temporary errors; go back to sign-in when the step is over or the tunnel failed after a correct code.

## Plan (planner)
**The issue's table was corrected to match the real server.** A wrong code on `login/otp` returns `invalid_credentials`, not `invalid_code`, and the step ends at the third wrong code (Hifaz `client_calls.go:405-451`). So today the first wrong code already sent the user back to the password screen.

New `signInFail()` in `startSession`, applied while the code screen is showing:

| Answer | App |
|---|---|
| wrong code (`invalid_credentials`) | Stay with the "code does not match" text, up to 3 tries; at the 3rd, back to sign-in. |
| network, `timeout`, `rate_limited`, `clock_skew`, 5xx | Stay with the step kept. |
| `invalid_step` | Back to sign-in with the new `signin_step_expired` text. |
| other errors | Back to sign-in. |
| service failure after a correct code | Sign out on the server, then back to sign-in. |

- The step remembers its WireGuard key.
- The fakeserver gets the real behaviour: `invalid_step`, the 5-minute expiry and 3 tries.
- Tests cover a wrong code, three wrong codes, an expired step, a lost answer, and a service failure.
- Interop: new `TestWinClientSignInCodeStep`.

Decided without asking: after the third wrong code, the existing "sign-in failed" text is shown.

## Review (reviewer)
- Rounds: 1
- Blocking findings and how they were fixed: none. The reviewer ran `make check` again, the new tests 20 times with `-race`, and the interop against `../Hifaz`; all pass, and `../Hifaz` stayed clean. Confirmed:
  - The step rules match the real server (`client_calls.go:405-451`).
  - Lockout comes no sooner than before: each wrong code is one failure, as before, and `invalid_step` records none.
  - Every path clears the busy state, and Connect always does something.
- Fixed after review (one note was a real bug in the new code):
  - The page cleared the code field only when it saw a busy view followed by an error. On Windows the views are merged, so the busy view can be skipped.
  - Now the field is cleared as soon as the code is sent, and focused when an error comes back on the code screen (`app.js`; the `lastBusy` flag is removed). `make check` passes after the fix.
- Notes left for later (non-blocking):
  1. **Error after a correct code:** after a 5xx or a lost answer to a correct code, the server has already ended the step. The next Connect gets `invalid_step` and says "timed out", which is not what happened. It ends cleanly, with no lockout cost.
  2. **The app's count of wrong codes can fall behind the server's** when the answer to a wrong code is lost. It ends with one extra request and `invalid_step`, at no lockout cost. Not tested.
  3. **`invalid_signature` on the code step goes back to sign-in** although the server keeps the step. This is acceptable: a retry wouldn't help.
  4. **`c.signin` is not cleared on disconnect or add server.** That was already the case and is harmless.
  5. **Test gaps:**
     - no table test of `keepsStep` for `rate_limited`, `timeout`, `clock_skew` or 5xx;
     - no test of a WireGuard key mismatch.
